Short Description of My Application

My application is a three-tier web system consisting of a frontend (Nginx), a backend API (Flask + Gunicorn), and a MySQL database. When the user opens the frontend page, the browser sends a request to the backend's /api endpoint. The backend connects to the MySQL database, reads a greeting message, inserts a new visitor record, retrieves the total visitor count, and fetches the current database time. It then returns all this information as JSON. The frontend displays the message, the database time, and the visitor count, demonstrating full communication between all three tiers and confirming that the database persists data across requests and pod restarts.

ConfigMaps and Secrets for Container Configuration

In Kubernetes, both ConfigMaps and Secrets are used to provide configuration data to containers, but they serve different purposes. A ConfigMap stores non-sensitive configuration values such as database hostnames, usernames, and application settings. These values are injected into containers as environment variables or mounted as configuration files, allowing the application to read them at runtime without hard-coding them into the image. In contrast, a Secret is designed specifically for sensitive information like passwords, API keys, and tokens. Secrets are stored in a protected, base64-encoded format and are only accessible to authorized pods. In my application, the backend deployment uses a ConfigMap to receive safe configuration values such as DB_HOST, DB_NAME, and DB_USER, while a Secret provides the sensitive DB_PASSWORD and MYSQL_ROOT_PASSWORD. This separation ensures that containers receive all necessary configuration while keeping confidential data secure and following Kubernetes best practices.

Database Persistence in Rahti

In this application, the MySQL database must use persistent storage so that data is not lost when containers restart. In Rahti, I created a PersistentVolumeClaim (PVC) and attached it to the MySQL deployment, ensuring that all database files under /var/lib/mysql are stored on Rahti's persistent storage backend rather than inside the pod's ephemeral filesystem. To verify persistence experimentally, I inserted several rows into the counter table through the backend API and confirmed the visitor count increased. Then I manually deleted the MySQL pod from the Rahti console. When Rahti automatically recreated the pod, I connected to the database again and checked the counter table; all previously stored rows were still present. This demonstrated that the data survived pod replacement and that the PVC was functioning correctly. Persistence in Rahti differs from the Docker volume used in earlier exercises because Docker volumes store data locally on the developer's machine, while Rahti PVCs store data on a network-backed persistent storage system managed by the cluster. This means data in Rahti remains intact even if pods are rescheduled to different nodes, whereas Docker volumes only persist as long as the local Docker environment remains unchanged.

Comparison of Rahti and cPouta

Rahti and cPouta are both cloud services provided by CSC, but they serve different purposes and operate at different abstraction levels. cPouta is an Infrastructure-as-a-Service (IaaS) platform where the user manages virtual machines directly. In cPouta, you are responsible for installing and configuring everything yourself, including the operating system, web server, security updates, networking rules, and storage. This gives full control but also requires more manual work. In contrast, Rahti is a Platform-as-a-Service (PaaS) environment built on Kubernetes/OpenShift. Instead of managing virtual machines, you deploy container images, and Rahti automatically handles scheduling, scaling, networking, routing, health checks, and persistent storage. Rahti uses Deployments, Services, Routes, Secrets, and ConfigMaps to manage applications declaratively, while cPouta requires manual configuration through SSH and system administration. In summary, cPouta gives raw infrastructure control, while Rahti provides a higher-level, automated platform for running containerized applications with less operational overhead.

Rahti uses a Deployment controller that defines the desired number of replicas. When a pod is deleted, Kubernetes detects that the actual number of pods is less than desired and automatically creates a replacement. This behavior proves self-healing — Rahti maintains the desired state of the application without manual intervention.

2. Scaling Experiment

I opened Rahti → Workloads → Deployments and selected my backend deployment. In the deployment settings, I changed the number of replicas from 1 to 3. I refreshed the frontend several times to confirm the application still worked.

Rahti created new pods automatically as soon as I increased the replica count. The new pods had different names but identical configuration. The frontend continued working normally — no downtime.

In Rahti, the frontend does not need to know the IP addresses of individual backend pods because Kubernetes provides a stable communication layer through a Service. Each backend pod receives its own internal IP address, but these IPs change whenever pods are restarted, scaled, or replaced. Instead of connecting directly to pod IPs, the frontend sends its requests to the backend Service, which has a permanent virtual IP and DNS name. The Service automatically discovers all backend pods using label selectors and forwards incoming requests to whichever pods are currently running. This means the frontend always communicates with a single, stable endpoint, while Kubernetes handles load balancing and routing behind the scenes. As a result, the application continues working even when pods are deleted, recreated, or scaled, demonstrating how container orchestration abstracts away pod-level networking details.

3. Application Update Experiment

I made a small change to my backend application. I rebuilt the Docker image locally and pushed the new version to Docker Hub with a new tag. In Rahti, I opened Workloads → Deployments → backend. I edited the deployment and changed the container image from the old tag to the new one. After saving, Rahti automatically started a rolling update: New pods began appearing with the updated image. Old pods started terminating one by one. I waited until all new pods reached Running state. I refreshed the frontend route to confirm the updated backend behavior.

Rahti immediately pulled the new image tag and created new backend pods. The old pods did not disappear instantly — Rahti replaced them gradually. During the update, the application stayed online with no downtime. Once the rollout finished, only the new pods were running. The frontend showed the updated backend output. This confirmed that Rahti handles updates automatically and safely without breaking the application.

Most Important Problem Encountered and How I Solved It

The most significant problem I encountered during the project was that the backend could not connect to the MySQL database after deploying the application to Rahti. The frontend loaded correctly, but the backend API returned errors, and the visitor counter did not update. After investigating the backend logs, I discovered that the database hostname and credentials were not being passed correctly to the backend container. In Rahti, environment variables must be provided through ConfigMaps and Secrets, and the backend deployment must explicitly reference them. I solved the issue by creating a Secret for the database password and a ConfigMap for the non-sensitive settings, then updating the backend Deployment YAML to include these values under the env: section. Once the deployment was redeployed with the correct environment variables, the backend successfully connected to MySQL, the /api endpoint returned the expected JSON, and the visitor counter began increasing normally. This confirmed that the configuration was correct and that all three tiers were communicating properly.
